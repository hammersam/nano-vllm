# TopK 算法设计对比分析

## 问题背景

对于 128k token 序列长度，k=2048 的 TopK 选择问题：
- 当前 Radix-based 实现的 theoretical occupancy 只有 50%
- 主要瓶颈是 shared memory 使用过多 (128KB+)
- 需要探索更高效的实现方案

## ⚠️ 重要发现 (H100 Benchmark)

```
torch.topk:              0.183 ms | Accuracy: 1.0000
Radix TopK (original):   0.103 ms | Accuracy: 1.0000  ← 最快！
Radix Split-KV (2-stage): 0.151 ms | Accuracy: 1.0000
Radix Fused (last block): 0.147 ms | Accuracy: 1.0000
```

**关键结论**：
1. **原始单 block radix topk 已经比 torch.topk 快 1.8x！**
2. **50% occupancy 不是真正的瓶颈** - 可能因为 kernel 是 memory-bound
3. **多 block 方案反而更慢** - 增加了同步和内存访问开销

## 方案 1: Warp-level Bitonic Merge TopK

### 核心思想

```
                    ┌─────────────────────────────────────────┐
                    │           128k tokens                    │
                    └─────────────────────────────────────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                 ▼
            ┌───────────┐     ┌───────────┐     ┌───────────┐
            │  Warp 0   │     │  Warp 1   │ ... │  Warp 31  │
            │  4k tok   │     │  4k tok   │     │  4k tok   │
            └─────┬─────┘     └─────┬─────┘     └─────┬─────┘
                  │                 │                 │
                  ▼                 ▼                 ▼
            ┌───────────┐     ┌───────────┐     ┌───────────┐
            │ Local TopK│     │ Local TopK│     │ Local TopK│
            │   2048    │     │   2048    │     │   2048    │
            └─────┬─────┘     └─────┬─────┘     └─────┬─────┘
                  │                 │                 │
                  └────────────┬────┴────────────────┘
                               ▼
                    ┌─────────────────────┐
                    │   Bitonic Merge     │
                    │   (Warp Shuffle)    │
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │   Final TopK 2048   │
                    └─────────────────────┘
```

### 关键技术

1. **Warp Shuffle 通信**
   ```cuda
   // 避免 shared memory，使用寄存器通信
   val = __shfl_xor_sync(0xffffffff, val, offset);
   ```

2. **Bitonic Merge Network**
   ```
   阶段 1: 比较距离 1 的元素对
   阶段 2: 比较距离 2, 1 的元素对
   阶段 3: 比较距离 4, 2, 1 的元素对
   ...
   ```

3. **Register 存储候选**
   - 每个 thread 用 register 存 64 个候选
   - 32 threads × 64 = 2048 个候选 per warp

### 优劣分析

| 优势 | 劣势 |
|------|------|
| ✅ 精确结果 | ❌ Bitonic merge O(k log²k) 复杂度 |
| ✅ 低 shared memory | ❌ 实现复杂 |
| ✅ 高并行度 | ❌ k 大时 merge 开销大 |
| ✅ Warp shuffle 高效 | ❌ Register 压力大 |

### 适用场景

- k 较小 (< 1024)
- 需要精确结果
- GPU occupancy 是主要瓶颈

## 方案 2: Merge-based TopK

### 核心思想

```
                    ┌─────────────────────────────────────────┐
                    │           128k tokens                    │
                    └─────────────────────────────────────────┘
                                      │
        ┌─────────┬─────────┬─────────┼─────────┬─────────┬─────────┐
        ▼         ▼         ▼         ▼         ▼         ▼         ▼
    ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
    │Block 0│ │Block 1│ │Block 2│ │Block 3│ │Block 4│ │Block 5│ │Block 6│...
    │ 16k   │ │ 16k   │ │ 16k   │ │ 16k   │ │ 16k   │ │ 16k   │ │ 16k   │
    └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘ └───┬───┘
        │         │         │         │         │         │         │
        ▼         ▼         ▼         ▼         ▼         ▼         ▼
    [top-2k]  [top-2k]  [top-2k]  [top-2k]  [top-2k]  [top-2k]  [top-2k]
        │         │         │         │         │         │         │
        └─────────┴─────────┴────┬────┴─────────┴─────────┴─────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │    K-way Merge          │
                    │  (Tournament Tree)      │
                    └────────────┬────────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │     Final TopK 2048     │
                    └─────────────────────────┘
```

### 关键技术

1. **Stage 1: 并行块选择**
   - 每个 block 独立处理 chunk
   - 用 min-heap 或 partial sort 选出 local top-k
   - 无需 inter-block 同步

2. **Stage 2: Tournament Tree Merge**
   ```
        ┌───────────────────────────────────┐
        │              Winner               │  <- 根节点: 全局最大
        └───────────────┬───────────────────┘
                       /                 \
            ┌─────────┴─────┐     ┌─────┴─────────┐
            │   Winner 0-3  │     │   Winner 4-7  │
            └───────┬───────┘     └───────┬───────┘
                   /    \              /       \
               ... (二叉树结构) ...

        叶子节点: 各 chunk 的当前最大元素
   ```

3. **增量更新**
   - 每次输出一个 winner 后，只需更新 O(log m) 个节点
   - m = chunk 数量

### 优劣分析

| 优势 | 劣势 |
|------|------|
| ✅ 高并行度 | ❌ 需要两个 kernel |
| ✅ Block 间独立 | ❌ Stage 2 可能成为瓶颈 |
| ✅ 精确结果 | ❌ 需要额外全局内存 |
| ✅ 易于实现 | ❌ Kernel launch 开销 |

### 适用场景

- 需要精确结果
- 数据量非常大 (>= 256k)
- GPU 有大量 SM 可用

## 方案 3: Sample Sort TopK

### 核心思想

```
Step 1: 采样估计分布
┌─────────────────────────────────────────────────────────────┐
│  ●   ●   ●   ●   ●   ●   ●   ●   ●   ●  <- 采样 1024 点    │
│ 128k tokens                                                 │
└─────────────────────────────────────────────────────────────┘
                            │
                            ▼
            ┌───────────────────────────────────┐
            │ 排序采样点，估计第 k 大 ≈ threshold │
            │     [s₁, s₂, ... s₁₀₂₄]           │
            │            ↑                      │
            │      threshold = s[k*1024/128k]   │
            └───────────────────────────────────┘
                            │
Step 2: 过滤                ▼
┌─────────────────────────────────────────────────────────────┐
│  █ █ █   █   █ █   █ █ █   █  <- 只保留 > threshold 的元素 │
│  (约 2k~4k 个候选)                                          │
└─────────────────────────────────────────────────────────────┘
                            │
Step 3: 精确排序            ▼
            ┌───────────────────────────────────┐
            │   对 ~4k 候选精确排序              │
            │   取前 2048 个                     │
            └───────────────────────────────────┘
```

### 关键技术

1. **采样策略**
   - 均匀采样: `sample[i] = input[i * n / num_samples]`
   - 随机采样: 更好的统计特性，但需要随机数
   - 分层采样: 每个 warp 贡献一部分采样

2. **Threshold 估计**
   ```
   sorted_samples = sort(samples)  // 降序
   threshold_idx = k * num_samples / seq_len
   threshold = sorted_samples[threshold_idx] * safety_margin
   ```

3. **两遍扫描**
   - 第一遍: 计数 > threshold 的元素数量
   - 第二遍: 收集这些元素并排序

### 优劣分析

| 优势 | 劣势 |
|------|------|
| ✅ 极高并行度 | ❌ 近似结果 |
| ✅ 最小 shared memory | ❌ 采样可能不准 |
| ✅ O(n) 复杂度 | ❌ 需要两遍扫描 |
| ✅ 实现简单 | ❌ threshold 难以精确估计 |

### 精度分析

```
假设数据服从正态分布 N(0, 1):
- 采样 1024 点估计第 98.4% 分位数 (k=2048, n=128k)
- 标准误差 ≈ σ / √n = 1/√1024 ≈ 0.031

实际准确率:
- 通常 > 99% 的 top-k 元素能被正确选出
- 边界附近的元素可能有误差
```

### 适用场景

- 可以接受近似结果
- 需要最高性能
- 数据分布较为均匀

## 方案 4: 改进的 Radix TopK (Parallel Histogram)

### 核心思想

```
原始 Radix:
  所有 threads ──atomic_add──> 单个 histogram [256]
                                    ↑
                             严重竞争！

改进 Radix:
  ┌──────────────────────────────────────────────────────────┐
  │                     128k tokens                          │
  └──────────────────────────────────────────────────────────┘
        │           │           │           │           │
        ▼           ▼           ▼           ▼           ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ Warp 0  │ │ Warp 1  │ │ Warp 2  │ │  ...    │ │ Warp 31 │
  │ hist[256]│ │ hist[256]│ │ hist[256]│ │        │ │ hist[256]│
  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘
       │           │           │           │           │
       └───────────┴───────────┼───────────┴───────────┘
                               │
                               ▼  (reduce)
                    ┌─────────────────────┐
                    │  Global hist [256]  │
                    └─────────────────────┘
```

### 关键技术

1. **Warp-local Histogram**
   - 每个 warp 维护独立的 histogram
   - 减少 atomic 冲突 (32x)

2. **Parallel Reduction**
   ```cuda
   // 每个 thread 负责合并一个 bin
   for (int w = 0; w < NUM_WARPS; w++) {
       global_hist[bin] += warp_hist[w][bin];
   }
   ```

3. **Shared Memory 布局优化**
   ```
   原始: histogram [257] × 4B = 1028B
         input_idx [2][4096] × 4B = 32KB
         总计 ≈ 33KB (理论)

   但实际编译器可能分配 128KB+ (因为数组对齐等)
   ```

### 优劣分析

| 优势 | 劣势 |
|------|------|
| ✅ 保持 O(n) 复杂度 | ❌ Shared memory 仍较大 |
| ✅ 减少 atomic 冲突 | ❌ 仍是单 block |
| ✅ 精确结果 | ❌ Occupancy 提升有限 |
| ✅ 改动小 | |

## 为什么 50% Occupancy 不是瓶颈？

### 理论分析

```
Occupancy 的作用: 隐藏内存延迟 (latency hiding)

但如果 kernel 已经是 memory bandwidth bound:
  └─ 更高的 occupancy 不会提高吞吐量
  └─ 内存带宽已经饱和

Radix TopK 的特点:
  └─ 大量顺序内存读取 (128k × 4B = 512KB per batch)
  └─ 计算量很小 (只是 histogram 累加)
  └─ 实际瓶颈是内存带宽，不是计算
```

### 实验验证

即使 50% occupancy，单 block radix 仍然最快的原因：
1. **内存访问模式更优**：连续读取，充分利用 L2 cache
2. **无同步开销**：单 block 不需要 inter-block 同步
3. **无重复工作**：多 block 方案需要 9 次 radix pass，单 block 只需 1 次

## 推荐方案 (更新)

### 对于 DeepSeek-V3 的 MLA Attention TopK:

1. **首选: 原始 Radix TopK (单 block)**
   - ✅ 已经是最快的实现
   - ✅ 精确结果
   - ✅ 代码简单

2. **何时考虑多 block**:
   - 序列长度 > 256k (单 block 内存访问次数过多)
   - Batch size 很小 (SM 利用率不足)

3. **不推荐**: Sample Sort
   - 理论上应该更快，但实现复杂度高
   - 近似结果可能影响 attention 质量
